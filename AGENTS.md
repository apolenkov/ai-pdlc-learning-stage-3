# Правила отдельного входа в ступень 3

- Это готовый поздний старт R3 с существующим приложением. Основной маршрут R1→R2→R3 продолжается в одном личном checkout, созданном на R1, и не обязан клонировать этот репозиторий; шаблоны `docs/templates` на этом маршруте не используются.
- Для отдельного старта сначала создаётся личная `course/<login>/stage-3-base`, затем рабочая `course/<login>/stage-3-reset-years`; planning MR направляется из рабочей ветки в личный target внутри корпоративного fork, не в общую `main`; после двух review его можно смёржить в личную base-ветку fork. Защиту эталона не обходить; правила собственного репозитория задаёт его владелец.
- OpenSpec здесь repo-local: действующие требования находятся в `openspec/specs`, история — в `openspec/changes/archive`, согласованное не реализованное поведение — в активных Changes.
- На ручной R3 создаётся или продолжается `add-reset-and-years-term` через native `status` и `instructions`. ИИ не обязателен. Apply, правки приложения/runtime-тестов, закрытие tasks и архивирование Change запрещены.
- Исходное состояние — только поведение существующего приложения, подтверждённое кодом и проверками. Отсутствующее поведение не превращать в main spec или факт реализации.
- Необязательное 3‑ИИ выполняется в отдельной `course/<login>/stage-3-ai-payment-summary` от личной R3, создаёт `add-payment-summary` — коррекцию формулы уже выводимых общей суммы и переплаты, а не новые поля — в VS Code с расширением Kilo Code (native `.kilo/skills` уже в репозитории; OpenCode — продвинутая альтернатива) и сохраняет исходный Change. Apply запрещён; MR идёт из ветки 3‑ИИ (source) в личную `course/<login>/stage-3-reset-years` (target).
- Перед коммитом проверять diff и состав staged-файлов; для учебной ветки и MR достаточно актуального diff — полный SHA записывайте только для происхождения, передачи или по требованию организаторов. Не печатать выученные SHA и не заменять недоступный источник текущей `main`.
- `npm run check` сохраняется как проверка исходного состояния. Его успех не доказывает будущие функции и не требуется превращать в реализацию ради завершения курса.
- Человеческие review относятся к одному актуальному diff. ИИ и автоматическая проверка не являются одобрением людей.
- В R4 передаются все активные Changes и фактический набор main specs, даже если он пуст. SHA планирования и service pin — независимые доказательства разных ролей; их репозитории или значения могут совпасть либо различаться.
- Store используется только в личном product-meta. Не переносить Store-only конфигурацию в общую `main` этого примера и не поддерживать две редактируемые копии контракта планирования.
- `.workspace` в product-meta всегда read-only. Для будущей реализации разработчик создаёт отдельный checkout сервиса после отдельного разрешения.
- Не менять Store-регистрацию, не применять force и не сбрасывать чужие изменения автоматически. При неверной папке, ветке, root, SHA или грязном дереве остановиться с точной причиной.
- Не сохранять секреты, персональные данные, рабочие корпоративные документы и выдуманные Jira-ссылки.
